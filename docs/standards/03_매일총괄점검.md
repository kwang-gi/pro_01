# 03 매일 총괄 점검 (08:07)

목적: 루틴이 제대로 돌았는지 확인하고, 시키지 않아도 다음 단계를 하나씩 진행한다. 담당은 Opus 5.5 코디네이터이며 직접 길게 일하지 않고 분해·검수만 한다.

## 절차 (순서 고정)

| 순서 | 할 일 | 기준 |
|---|---|---|
| 1 | 읽기 | `plans/총괄점검-로그.md` 최신 항목, `plans/자동화-현황.md`, `data/status.json`, 오늘 뉴스 요약 파일 존재 여부 |
| 2 | 고장 먼저 | 06:20 깃허브 예약 실행 여부, 06:50 요약 저장 여부, 07:43 아이디어뱅크 실행 여부. 이상이 있으면 새 단계보다 복구가 먼저 |
| 3 | 다음 단계 1개 고르기 | 하루에 1개만. 실행계획·자동화 추천·아이디어뱅크 요약의 다음 행동 중 지금 막힘이 가장 큰 것 |
| 4 | 워커 분업 | 코디네이터는 짧게 라우팅만. 대량·반복은 Haiku, 구현·정리는 Sonnet 워커에게 맡기고 판정은 모델 분업 기준표를 따른다 |
| 5 | 검증 | 만든 것은 실제로 한 번 돌려 본다. 링크는 원자료와 대조하고, 저장한 파일은 다시 읽는다 |
| 6 | 로그 5줄 | 아래 양식으로 `총괄점검-로그.md` 맨 위(최신이 위)에 추가 |
| 7 | 3줄 보고 | `05_보고형식.md` 따름. 확인된 결과만 |

## 고장 복구 규칙 (실제 사례)

- 깃허브 예약 미실행: `workflow_dispatch` 로 수동 실행, 출처 11/11 과 현황판 갱신을 확인. 10/9 08:08 에 이렇게 복구했고 07:47 예비 예약을 추가했다(PR #6).
- 예비 예약도 안 돌면(10/9·10/10 연속 0건): 06:50 뉴스 루틴이 스스로 수동 실행하도록 절차에 넣어 두었다. 점검은 그 결과를 확인한다.
- 같은 일이 2번 이상 실패하면 원인 분석은 Opus가 한다. 원인을 찾으면 다시 아래 모델에 돌려준다.

## 로그 양식 (템플릿)

````
## YYYY-MM-DD 08:07
- 고장 없음 또는 고장: <무엇이, 어떻게 복구했는지 한 줄>
- 단계: <오늘 고른 1개> → <결과 파일 경로>. <핵심 수치 한 줄>
- 검증: <실제로 확인한 것: 링크 대조, 파일 재확인, 실행 기록>
- 분업: 고장 판단·대상 선정·검수=Opus · <작업>=Sonnet · <작업>=Haiku · <작업>=파이썬(0원)
````

규칙: 5줄 이내. 확인 못 한 것은 "미확인". 실제 결과 파일이 있을 때만 "완료"라고 쓴다.

## 하지 않는 것

- 사용자에게 해라·눌러라·승인해라 요청하기 (사전 승인 범위 안의 일은 그냥 진행).
- 예외 3가지(결제, 복구 불가 삭제, 비밀값 생성·추측)는 진행하지 않고 로그에 "보류"로만 남긴다.
