## 1. 한눈에 보기 (5줄 요약)

1. **무엇**: 지인이 소개팅 상대를 추천(주선)하고 성사되면 수수료를 받는 웹 서비스. 결혼정보회사 아님 — 등기 인증 지인 소개 + 무관용 신고 시스템으로 안전한 만남만 딱 3번(또는 선택 횟수) 주선.
2. **누가 돈 냄**: 신청자(소개받는 사람)가 주선비·성사비를 냄. 지인 본인은 돈 내는 걸 모름(수수료 비공개).
3. **돈이 어떻게 도나**: 신청자 무통장 입금 신고 → 관리자가 눈으로 확인 → 잔고 반영 → 성사 시 주선자·플랫폼 분배.
4. **선택은 전부 관리자 옵션**: 요금·비율·성사기준·예치금 방식 등 정책값은 전부 관리자 페이지 스위치로 켜고 끄며, 바꾸는 즉시 반영(재배포 불필요).
5. **지금 상태**: `linker-app/`에 MVP 스캐폴드 완성(빌드 통과, 흐름 검증됨). 이번 v3는 그 위에 **settings(설정) 테이블·관리자 옵션 확장·보안 로드맵·결제 로드맵**을 얹는 설계도.

## 2. 목표와 범위

### MVP에 넣는 것
- 회원가입(역할: 남성 신청자/여성 신청자/주선자/관리자) + 가입 인증(문자/등기 [모의])
- 지인 등록(성비 룰) + 지인 동의(알림톡 [모의])
- 소개 제안(주선자→신청자) — v3에서 **요청형(신청자→주선자 게시판)** 추가
- 만남 1~3회(또는 선택 횟수) 기록 → 성사 판정
- 무통장 입금 신고 → 관리자 확인 → 잔고 반영
- 성사비 원장, 주선자 정산
- 무관용 신고(4대 조항) → 몰수 + 자동 공지
- 관리자 콘솔(가입 승인·입금 확인·신고 처리·공지·정산)
- **v3 신규**: 관리자 설정(settings) 탭 — 모든 정책값 실시간 변경
- **v3 신규**: 버전 체크 API (로그인 시 업데이트 안내)
- **v3 신규**: 개인정보 분리 저장 구조(자리 마련)

### MVP에 안 넣는 것 (이후 단계)
- 실제 PG(토스 등) 연동, 실제 SMS/등기/알림톡 연동 — 전부 [모의] Provider 유지, 교체 지점만 마련
- 사진 업로드(텍스트 프로필만, 사진은 블럭 자리만)
- Tauri 설치형 클라이언트(VIP용) — 서버가 커지면 도입
- PostgreSQL 등 DB 이전 — 공란(추후 결정)
- 다중 서버·페일오버·유령 DB 등 고급 보안 인프라 — 공란(로드맵만 기재)

## 3. 최상위 설계 원칙

| # | 원칙 | 의미 |
|---|---|---|
| 1 | **관리자 전체 제어·즉시 적용** | 모든 정책(요금·비율·모드·기준)은 옵션으로 구현, 관리자 페이지에서 스위치 변경 시 재배포 없이 즉시 반영. 안 쓰는 옵션도 삭제 아닌 비활성 보존 |
| 2 | **블럭(톱니바퀴) 교체형** | 결제·문자·알림·사진 등 외부 연동은 전부 Provider 인터페이스 + Mock 구현체. 실서비스 연동 시 그 파일만 교체, 나머지 코드 무수정 |
| 3 | **개인정보 분리** | 신상 정보(이름·연락처·주소 등)는 매칭·정산 로직이 도는 메인 DB와 분리 보관 원칙. MVP는 같은 SQLite 파일 내 테이블 분리로 시작 → 이후 별도 DB로 물리 분리(공란) |
| 4 | **지인에게 수수료 숨김** | 소개받는 지인(acquaintance)은 자신을 데려온 주선자가 수수료를 받는다는 사실을 화면 어디서도 볼 수 없음. 영업성 접근 최소화 목적 |

### 6.2 ★신규 — settings 테이블 설계

**목적**: v2 최상위 원칙 "모든 정책을 관리자 페이지에서 선택 → 즉시 적용"을 구현하는 핵심 테이블. 전역 기본값과 클라이언트(개별 PC/계정)별 오버라이드(덮어쓰기)를 분리해서, 특정 유저·특정 단말에만 다른 정책을 걸 수 있게 한다.

```
CREATE TABLE settings_global (
  key TEXT PRIMARY KEY,        -- 예: 'broker_rate_default', 'deposit_mode', 'match_threshold_mode'
  value TEXT NOT NULL,         -- 실제 값(JSON 문자열로 저장 — 숫자/문자/구조체 모두 대응)
  value_type TEXT NOT NULL,    -- 'number' | 'string' | 'boolean' | 'json'
  category TEXT NOT NULL,      -- 'fee'(요금) | 'match'(성사기준) | 'deposit'(예치금) | 'ui'(화면) 등
  label_ko TEXT NOT NULL,      -- 관리자 화면에 보여줄 한글 설명
  updated_at TEXT NOT NULL,
  updated_by INTEGER REFERENCES users(id)
);

CREATE TABLE settings_override (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  scope_type TEXT NOT NULL,    -- 'user'(특정 계정) | 'client'(특정 PC/기기 식별자)
  scope_id TEXT NOT NULL,      -- user_id 또는 client_id(기기 지문)
  key TEXT NOT NULL,           -- settings_global.key와 동일 키 체계
  value TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  updated_by INTEGER REFERENCES users(id),
  UNIQUE(scope_type, scope_id, key)
);
```

- **즉시 적용 메커니즘**: 값 변경 시 재배포·재시작 불필요. API가 매 요청마다 `settings_global` + 해당 유저/클라이언트의 `settings_override`를 조회해 **오버라이드 우선**으로 병합한 값을 사용(간단한 조회 함수 하나로 전체 서버가 공유). 캐시를 쓸 경우 짧은 TTL(수명, 예: 5~10초)만 적용해 "즉시성"을 해치지 않음.
- **우선순위**: `settings_override(client) > settings_override(user) > settings_global > 코드 기본값`
- **비활성 보존 원칙**: 옵션을 안 쓰기로 해도 행(row)을 지우지 않고 `value`만 꺼둔 상태로 둠(예: `deposit_mode = 'B'`로 두면 A모드 관련 값은 존재하되 미사용).

## 7. 프런트 설계

### 7.1 역할별 화면 지도

| 역할 | 화면 | 기능 |

| | **`/admin/settings` (v3 신규)** | 아래 7.2 상세 |

## 8. 보안·방어 설계

### 8.1 외부 침입 방어 (MVP~단기)

> ★0706 확정: MVP 단계에서는 방어 구현을 전부 보류(공란) — 아래 표는 설계 자리만. 외부 공개(11장 배포 ②~③ 단계) 전에 일괄 착수.

| 항목 | 현재 | 실서비스 전 필수 조치 |
|---|---|---|
| 로그인 보호 | 세션 쿠키, 평문 비밀번호 [README 명시 한계] | bcrypt 등 해시 처리 필수 — 「공란, 착수 전」 |
| 요청 속도 제한(rate limit) | 없음 | 로그인·입금신고 등 API에 요청 속도 제한(짧은 시간 반복 요청 차단) 적용 — 「공란」 |
| 입력 검증 | 라우트별 기본 타입 체크 수준 | 서버 측 스키마 검증 라이브러리(zod 등) 도입 — 「공란」 |
| 권한 분리 | role 체크(신청자/주선자/관리자) 존재 | 세밀한 권한(예: 내 데이터만 조회) 전수 점검 — 「공란」 |

### 8.2 개인정보 분리 저장 (원칙 3 구현)

- MVP 단계: 이름·생년·지역·직업 등은 `users`/`acquaintances` 테이블에 있으나, 상세 신상(실명 등기 주소 등 인증에만 쓰는 정보)은 별도 테이블로 분리해 매칭 로직 코드가 직접 조회하지 못하게 함 — 「공란: 분리 테이블 스키마 확정 전, 자리만 마련」
- 이후 단계: 물리적으로 다른 DB/서버로 완전 분리(자료정리 문서의 "유령 DB" 개념) — 「공란」

### 8.3 수수료 정보 숨김 규칙

- 지인(`acquaintances`)은 로그인 계정이 없는 프로필 레코드 — 애초에 화면에 접근 권한 없음(구조적으로 안전)
- 신청자·지인에게 노출되는 모든 화면(제안, 만남, 알림 문구)에서 `broker_rate`, `settlement` 관련 필드 미노출 — 코드 리뷰 체크리스트 항목으로 관리 필요 — 「공란: 자동 검수 스크립트」

### 8.4 현행 한계 (README 근거) 및 실서비스 전 필수 조치

| 한계 (linker-app/README.md 명시) | 실서비스 전 조치 |
|---|---|
| 비밀번호 평문 저장 | bcrypt 해시화 — 「공란」 |
| 주선자 보증금 계좌 개념 없음(연대 몰수 시 0 처리) | `ledger_accounts`에 주선자 보증금 필드 추가 — 「공란」 |

| 신고 대상 특정 어려움(지인은 로그인 계정 없음) | 신고 대상 식별 구조 개선 — 「공란」 |

### 8.5 장기 보안 로드맵 (자료정리 문서 참고, 아직 미착수)

- 빈 대문 서버(Gateway, DB 없이 안내만) + 유령 DB(내부망 전용) 분리 구조 — 「공란」

- 불변 인프라(서버 직접 수정 불가) + 불변 감사 로그 — 「공란」
- 다중 페일오버(공격 시 서버 폐쇄 후 예비 서버 전환) — 「공란」

## 9. 결제·정산 설계

### 9.1 현행 흐름 (무통장 입금)
1. 신청자가 입금 후 "입금 신고"(`deposit_requests`, kind=initial/final)
2. 관리자가 `/admin` 콘솔에서 육안 확인 → 승인(confirm)/반려(reject)
3. 승인 시 `ledger_accounts` 잔고 반영

### 9.2 예치금 모드 A/B (관리자 스위치)

| 모드 | 흐름 | 상태 |
|---|---|---|
| A. 선입금 모드 | 가입 즉시 예치금 5 + 주선비 1 선입금 요구 | 구현(현행 기본) |
| B. 신청 후 입금확인 모드 | 예치금 없이 신청 → 소개 성사 임박 시 입금 확인 후 연결 | 「공란 — 로직 자리만, 관리자 스위치로 전환 가능하게 설계」|

### 9.3 주선비 2종 원장

| 종류 | 금액 범위 | 시점 |
|---|---|---|
| 기본 주선비 | 7~10만 원(관리자 조정) | 소개 제안 수락 시 |
| 성공 사례비 | 50~80만 원(관리자 조정) | 3회(또는 선택 기준) 만남 성사 시 |

- 현 코드의 `TOTAL_SUCCESS_FEE = 10`(상대값), `broker_rate` 기본 0.5는 **설정값으로 이관 예정** — settings 테이블 연결이 v3 구현 1순위(6.2 참고)

### 9.4 몰수/환불

- 무관용 4대 조항(폭력·포교·사업·돈) 위반 확정 시: 가해자 예치금 전액 몰수 + 해당 건 주선자 연대 몰수 + 피해자 즉시 환불 + 자동 전체 공지
- 일반 환불: 매칭 이력 없으면 즉시 환불 / 있으면 환불 대기(유예) 후 관리자 처리
- 환불 계좌는 입금한 본인 명의 계좌로만(자금세탁 방지) — 계좌 검증 로직은 「공란 — 추후 결정」

### 9.5 PG(결제대행사) 연동 자리

- 현재: `TossProvider.stub.ts` 파일이 이미 자리로 존재(구현 없음, 인터페이스만)
- 실 연동 시: 웹훅(결제사가 보내는 입금 알림 신호)의 디지털 서명 검증 로직 추가 필요 — 「공란」
- 카드 결제 최소화, 현금성 결제(가상계좌) 우선 방침 유지

2. **우수 주선자 기준** — 성사 건수 기준(예: 월 3건 이상)인지, 성사율 기준(예: 80% 이상)인지?
3. **예치금 모드 A→B 전환 시 진행 중 건** — 이미 A모드로 낸 사람이 있는데 B로 바꾸면 그 사람 건은 어떻게 처리할지?
