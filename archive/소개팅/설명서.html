한눈에 보기 (5줄 요약)

  1. 무엇: 지인이 소개팅 상대를 추천(주선)하고 성사되면 수수료를 받는 웹 서비스. 결혼정보회사 아님 — 등기 인증 지인 소개 + 무관용 신고 시스템으로 안전한 만남만 딱 3번(또는 선택 횟수) 주선.
  2. 누가 돈 냄: 신청자(소개받는 사람)가 주선비·성사비를 냄. 지인 본인은 돈 내는 걸 모름(수수료 비공개).
  3. 돈이 어떻게 도나: 신청자 무통장 입금 신고 → 관리자가 눈으로 확인 → 잔고 반영 → 성사 시 주선자·플랫폼 분배.
  4. 선택은 전부 관리자 옵션: 요금·비율·성사기준·예치금 방식 등 정책값은 전부 관리자 페이지 스위치로 켜고 끄며, 바꾸는 즉시 반영(재배포 불필요).
  5. 지금 상태: linker-app/에 MVP 스캐폴드 완성(빌드 통과, 흐름 검증됨). 이번 v3는 그 위에 settings(설정) 테이블·관리자 옵션 확장·보안 로드맵·결제 로드맵을 얹는 설계도.

  • 회원가입(역할: 남성 신청자/여성 신청자/주선자/관리자) + 가입 인증(문자/등기 [모의])

  • 무통장 입금 신고 → 관리자 확인 → 잔고 반영
  • 성사비 원장, 주선자 정산
  • 무관용 신고(4대 조항) → 몰수 + 자동 공지
  • 관리자 콘솔(가입 승인·입금 확인·신고 처리·공지·정산)

최상위 설계 원칙

#원칙의미
1관리자 전체 제어·즉시 적용모든 정책(요금·비율·모드·기준)은 옵션으로 구현, 관리자 페이지에서 스위치 변경 시 재배포 없이 즉시 반영. 안 쓰는 옵션도 삭제 아닌 비활성 보존
2블럭(톱니바퀴) 교체형결제·문자·알림·사진 등 외부 연동은 전부 Provider 인터페이스 + Mock 구현체. 실서비스 연동 시 그 파일만 교체, 나머지 코드 무수정
3개인정보 분리신상 정보(이름·연락처·주소 등)는 매칭·정산 로직이 도는 메인 DB와 분리 보관 원칙. MVP는 같은 SQLite 파일 내 테이블 분리로 시작 → 이후 별도 DB로 물리 분리(공란)
4지인에게 수수료 숨김소개받는 지인(acquaintance)은 자신을 데려온 주선자가 수수료를 받는다는 사실을 화면 어디서도 볼 수 없음. 영업성 접근 최소화 목적

★신규 — settings 테이블 설계

목적: 최상위 원칙 "모든 정책을 관리자 페이지에서 선택 → 즉시 적용"을 구현하는 핵심 테이블. 전역 기본값과 클라이언트(개별 PC/계정)별 오버라이드(덮어쓰기)를 분리해서, 특정 유저·특정 단말에만 다른 정책을 걸 수 있게 한다.

CREATE TABLE settings_global (
  key TEXT PRIMARY KEY,        -- 예: 'broker_rate_default', 'deposit_mode', 'match_threshold_mode'
  value TEXT NOT NULL,         -- 실제 값(JSON 문자열로 저장 — 숫자/문자/구조체 모두 대응)
  value_type TEXT NOT NULL,    -- 'number' | 'string' | 'boolean' | 'json'
  category TEXT NOT NULL,      -- 'fee'(요금) | 'match'(성사기준) | 'deposit'(예치금) | 'ui'(화면) 등
  label_ko TEXT NOT NULL,      -- 관리자 화면에 보여줄 한글 설명
  updated_at TEXT NOT NULL,
  updated_by INTEGER REFERENCES users(id)
);

CREATE TABLE settings_override (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  scope_type TEXT NOT NULL,    -- 'user'(특정 계정) | 'client'(특정 PC/기기 식별자)
  scope_id TEXT NOT NULL,      -- user_id 또는 client_id(기기 지문)
  key TEXT NOT NULL,           -- settings_global.key와 동일 키 체계
  value TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  updated_by INTEGER REFERENCES users(id),
  UNIQUE(scope_type, scope_id, key)
);
  • 즉시 적용 메커니즘: 값 변경 시 재배포·재시작 불필요. API가 매 요청마다 settings_global + 해당 유저/클라이언트의 settings_override를 조회해 오버라이드 우선으로 병합한 값을 사용(간단한 조회 함수 하나로 전체 서버가 공유). 캐시를 쓸 경우 짧은 TTL(수명, 예: 5~10초)만 적용해 "즉시성"을 해치지 않음.
  • 우선순위: settings_override(client) > settings_override(user) > settings_global > 코드 기본값
  • 비활성 보존 원칙: 옵션을 안 쓰기로 해도 행(row)을 지우지 않고 value만 꺼둔 상태로 둠(예: deposit_mode = 'B'로 두면 A모드 관련 값은 존재하되 미사용).

2. 핵심 아키텍처 — "은폐와 분리"

구성요소역할
빈 대문 서버 (Gateway/Proxy)유저 최초 접점. DB 없음, 안내만. 털려도 얻을 것 0. 이상 징후 시 즉시 삭제(꼬리 자르기)
유령 DB (Ghost DB)비공개망(VPC) 내부, 인터넷 주소 없음. 대문 서버의 암호화 신호에만 반응
그림자 감시/백업 서버정산·블랙리스트 관리용 최소 데이터만 별도 보관. 서버 이동 시에도 블랙 정보 유지
다중 페일오버예비 대문 서버 다수 준비 → 1번 공격 시 폐쇄, 2번 가동. 클라이언트에 "1번 안 되면 2번" 로직 내장

3. 설치형 클라이언트 (Tauri)

  • 일렉트론보다 가벼운 Tauri로 PC 설치형 배포 (홈페이지 직접 다운로드, 웹스토어 미등록)

  • 서버에는 해시(암호화 쓰레기 데이터)만 → 압수수색·해킹에도 매칭 이력 추적 불가 (텔레그램 방식)
  • VIP 셀링 포인트: "서버가 털려도 누구랑 만났는지 알 수 없다"
  • 해커가 정상 유저로 잠입해도 본인에게 허용된 데이터 이상 절대 접근 불가 (은행 비유: 도둑이 계좌 만들어도 남의 금고 못 봄)

4. 데이터·통신 보안

  • 서버↔DB 통신: mTLS (디지털 인증서 상호 확인)
  • 저장 데이터: AES-256 필드 단위 암호화, 마스터 키는 HSM/대표 개인 기기에만

  • 불변 감사 로그(Audit Trail): 정산 버튼 누른 기록 수정 불가 — 흔적 지우기 원천 차단
