# AGENTS2.md — 프로젝트 재정비·멀티에이전트 운영 지시서

> 작성 목적: 기존 프로젝트의 현재 상태를 추측하지 않고, 먼저 전체 실사를 수행한 뒤 멀티에이전트 + Git 중심으로 재정비하기 위한 운영 지시서.
> 주의: 이 문서는 현재 코드 상태 보고서가 아니다. 실제 코드/폴더를 읽은 뒤 상태 문서를 별도로 만든다.

## 1. 가장 먼저 할 일 — 수정 금지, 전체 실사

- 프로젝트를 처음부터 새로 만들지 말 것.
- 기존 코드와 문서를 함부로 이동·삭제·개명하지 말 것.
- 먼저 전체 폴더를 읽기 전용으로 조사한다.
- 현재 실제 서비스 본체가 `linker-app/`, `ap/`, 또는 다른 폴더인지 반드시 확인한다.
- 어떤 파일이 실제 소스인지, 문서인지, 과거 지시문인지, 임시파일인지 분류한다.
- 현재 구현된 기능 / 미완성 기능 / 깨진 기능 / 중복 구현을 구분한다.
- 실사 전에는 “완성도”, “재작성 필요 여부”, “새로 시작해야 한다”를 단정하지 않는다.

## 2. 병렬 실사팀 구성

한 세션/한 에이전트가 프로젝트 전체를 독점하지 않는다.

- 팀 A: 프론트엔드 구조 및 화면별 구현 상태 조사
- 팀 B: 백엔드 / API / DB / 인증 구조 조사
- 팀 C: 문서 / 지시문 / 과거 계획 / 핸드오프 / 중복·폐기 후보 파일 조사
- 팀 D: 실행·빌드·테스트 관점에서 실제 동작 여부 조사
- 총괄: 각 팀 보고서를 통합하고 충돌·누락을 교차검증

중요:
- 같은 파일을 여러 에이전트가 동시에 수정하지 않는다.
- 실사 단계에서는 가능한 한 코드 수정 없이 조사와 문서화에 집중한다.

## 3. 공식 기억은 대화가 아니라 Git + 문서

대화창은 지시와 자문용이다.
프로젝트의 공식 상태는 반드시 파일로 남긴다.

최소 관리 문서:

- `CURRENT_STATE.md` — 현재 실제 구현 상태
- `TASK.md` — 해야 할 일 / 진행 중 / 완료
- `DECISIONS.md` — 중요한 결정과 이유
- `FILE_MAP.md` — 핵심 폴더·파일 역할 지도
- `PROBLEMS.md` — 오류·중복·미완성·기술부채
- `MASTER_PLAN.md` — 실사 완료 후 다시 짠 전체 실행계획

기존 `README`, `CLAUDE.md`, `AGENTS.md`, 최신 HANDOFF 문서는 삭제하지 않는다.
현재 체계와 충돌하는 부분은 총괄이 비교 후 정리한다.

## 4. 작업 종료 시 반드시 갱신

모든 작업자는 작업을 끝낼 때 다음을 수행한다.

1. `TASK.md` 상태 갱신
2. 실제 상태가 바뀌었으면 `CURRENT_STATE.md` 갱신
3. 중요한 설계·정책 결정이 있으면 `DECISIONS.md` 갱신
4. Git 변경사항을 명확한 단위로 남긴다
5. 다음 작업자가 대화 기록 없이 이어갈 수 있게 근거 파일 경로를 남긴다

## 5. Git 운영 방향

- 현재 폴더에 `.git`이 있는지 먼저 확인한다.
- `.git`이 있으면 기존 저장소 이력을 보존한다.
- `.git`이 없으면 기존 파일 백업 후 Git 저장소 초기화를 검토한다.
- GitHub 원격 저장소 존재 여부는 로컬 `.git` 존재 여부와 별개로 확인한다.
- 병렬 개발 시 작업 영역/브랜치를 분리하고, 같은 파일 동시 수정은 피한다.
- 통합 전 테스트 및 충돌 확인을 한다.

## 6. 역할 분담 방향

- Fable: 전체 구조 파악, 계획, 작업 분해, 합격/불합격 기준, 총괄 검수
- Sol: 설계 자문, 반대검토, 중요한 판단 교차검증
- Opus / Terra / Sonnet: 실제 구현, 코드 리뷰, 중간 검증
- Luna: 검색, 정리, 파일 분류, 로그 분석, 반복 심부름
- Codex: Git 기반 코드 작업, 병렬 실행, 파일 수정·테스트 작업자로 활용 가능

상위 모델이 모든 코드를 직접 작성하게 하지 않는다.
상위 모델은 기준과 구조를 만들고, 실행 모델이 그 기준에 따라 작업한다.

## 7. 검증 기준을 먼저 만든다

실제 코딩 전에 기능별로 아래를 명시한다.

- 합격 조건
- 불합격 조건
- 필수 테스트
- 금지사항
- 예외 처리
- 관련 파일/기능 범위

검증 모델은 자기 취향으로 평가하지 말고 위 기준에 따라 검사한다.

## 8. 지금 당장 총괄에게 시킬 첫 지시

프로젝트 전체를 수정하지 말고 먼저 실사하라.

반드시 아래를 보고하라.

- 실제 서비스 코드 본체가 어디인지
- 프론트 / 백엔드 / DB / API / 인증 구조
- 현재 구현 완료 기능
- 미완성 및 깨진 기능
- 중복·임시·과거 파일
- 현재 문서 체계와 실제 코드의 불일치
- Git 상태
- 유지 / 부분 재작성 / 전면 재작성 후보와 근거
- 멀티에이전트로 나눌 수 있는 작업 단위
- 각 작업 단위의 파일 충돌 가능성

실사 결과가 나오기 전에는 대규모 재작성에 착수하지 않는다.
