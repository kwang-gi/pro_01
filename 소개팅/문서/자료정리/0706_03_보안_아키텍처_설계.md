# 보안·아키텍처 설계 정리 (2026-07-06)

> 출처: 소개팅.mht 내 Gemini 대화 (보안 파트) + repo 03_시스템_아키텍처, 05_코드_보안_가이드(v1.1), 14_철통_보안_시방서

## 1. 설계 철학 (대표 요구사항 원문 기반)

- "서버가 털리거나 제재가 들어와도 내용을 오픈하고 싶지 않다"
- "신분 노출 꺼리는 사람들(VIP)은 PC에 별도 설치해서 쓸 수 있게"
- "메인 서버 문제 생기면 문어발 자르듯 즉시 버리고 다른 서버로"
- "개발자 백도어까지 차단하고 싶다"

## 2. 핵심 아키텍처 — "은폐와 분리"

| 구성요소 | 역할 |
|---|---|
| **빈 대문 서버 (Gateway/Proxy)** | 유저 최초 접점. DB 없음, 안내만. 털려도 얻을 것 0. 이상 징후 시 즉시 삭제(꼬리 자르기) |
| **유령 DB (Ghost DB)** | 비공개망(VPC) 내부, 인터넷 주소 없음. 대문 서버의 암호화 신호에만 반응 |
| **그림자 감시/백업 서버** | 정산·블랙리스트 관리용 최소 데이터만 별도 보관. 서버 이동 시에도 블랙 정보 유지 |
| **다중 페일오버** | 예비 대문 서버 다수 준비 → 1번 공격 시 폐쇄, 2번 가동. 클라이언트에 "1번 안 되면 2번" 로직 내장 |

## 3. 설치형 클라이언트 (Tauri)

- 일렉트론보다 가벼운 Tauri로 PC 설치형 배포 (홈페이지 직접 다운로드, 웹스토어 미등록)
- **민감 데이터(사진·상세 프로필·채팅)는 유저 기기에만 저장** — 제로 트러스트 + 종단 간 암호화(E2EE)
- 서버에는 해시(암호화 쓰레기 데이터)만 → 압수수색·해킹에도 매칭 이력 추적 불가 (텔레그램 방식)
- VIP 셀링 포인트: "서버가 털려도 누구랑 만났는지 알 수 없다"
- 해커가 정상 유저로 잠입해도 **본인에게 허용된 데이터 이상 절대 접근 불가** (은행 비유: 도둑이 계좌 만들어도 남의 금고 못 봄)

## 4. 데이터·통신 보안

- 서버↔DB 통신: **mTLS** (디지털 인증서 상호 확인)
- 저장 데이터: **AES-256 필드 단위 암호화**, 마스터 키는 **HSM/대표 개인 기기**에만
- **불변 인프라(Immutable Infrastructure)**: 개발자가 서버 직접 수정 불가, 배포는 자동 보안 스캔 + 대표 승인 잠금
- **불변 감사 로그(Audit Trail)**: 정산 버튼 누른 기록 수정 불가 — 흔적 지우기 원천 차단

## 5. 정산·금융 보안

- **결제와 신원의 분리**: 정산 서버에는 익명 ID(User_AX78)만 — 누구 돈인지 연결고리는 별도 금고 서버
- **웹훅 무결성 검증**: 결제사(토스 등) 입금 신호의 디지털 서명 100% 검증 → 가짜 입금 신호 차단
- 환불은 입금 본인 명의 계좌로만 (자금세탁 방지)

## 6. 소스 코드·DB 관리 (대표 개인 보안 습관 반영)

- 대표 방식: **VeraCrypt 암호화 가상 드라이브** + 제3의 비활성 계정 클라우드 보관 (= 콜드 스토리지, 전문가 수준 평가)
- 실무 표준: DB는 시간/일 단위 **자동 암호화 백업** → 별도 서버 적재. 개발자는 조회만 가능, 백업 반출은 대표 계정만
- AI 협업 시: .env / .gitignore 분리 설정을 AI에게 먼저 요청하는 습관
- 개발 인력 권한 분리: 코드 작성자와 DB/백업 관리자 분리 (한 명이 모든 열쇠 금지)
- 주기적 복구 테스트 ("한 달 전 데이터로 복구해봐")

## 7. 기술 스택 (03 문서 + 개발 방침)

- 웹 기반 반응형(모바일/PC) MVP 우선 — Next.js + Node.js 계열 (Gemini 추천)
- 개발 주체: **대표가 AI 3종(클로드 코드 + Codex/GPT + Gemini) 조합으로 직접 개발** 예정
- Tauri는 초기 MVP엔 불필요 — 사업 커지고 VIP 수요 생기면 웹사이트 포장용으로 도입
